Paradigmas de procesamiento

Streaming frente a Batch: dos mundos complementarios

Data in motion · Latencia ms–s

Procesamiento en Streaming

  • Procesa eventos según llegan (tiempo real o micro-batching).
  • Gestión compleja de estado, ventanas y eventos tardíos.
  • Casos: fraude, IoT, recomendaciones en vivo, precios bursátiles.
  • Stack: Kafka / Pulsar + Flink / Spark Streaming + Kinesis / Pub/Sub.
Data at rest · Ventanas horas–días

Procesamiento en Batch

  • Opera sobre grandes históricos en intervalos programados.
  • Recuperación sencilla mediante reintento sobre particiones.
  • Casos: ETL en data lakes, cierres BI, entrenamiento ML, logs.
  • Stack: Apache Spark, Snowflake/BigQuery, Trino, DuckDB.

Arquitectura Medallion: de ventanas cortas al Scheduling

El reto real de ingeniería

Orquestar sistemas heterogéneos: por qué cron falla

La realidad en producción

  • Fases en servidores y equipos distintos.
  • Tecnologías diversas y cajas negras (ERP, APIs SaaS, SQL, Spark, GPU).
  • Ventanas temporales dispares y grafos complejos de dependencias.

El colapso de cron + bash

  • Condiciones de carrera si una tarea tarda más de lo estimado.
  • Sin reintentos selectivos ni recuperación desde el paso fallido.
  • Cero alertas, cero SLAs y backfills manuales propensos a errores.
Requisitos de un orquestador (1 / 2)

Los 7 pilares de la orquestación: Pilares 1 al 4

1. Scheduling (Planificación)

Automatizar ejecuciones por horario (cron) o por eventos (fichero en S3, Asset).

Ej.: ETL diario de ventas a las 00:00 listo para BI a las 07:00.

2. Dependency Management

Garantizar orden topológico en el DAG: transformar solo cuando la extracción tenga éxito.

Ej.: bronze >> silver >> gold sin condiciones de carrera.

3. Monitoring & Alerting

Trazar estados, latencias y SLAs en tiempo real con alertas automáticas.

Ej.: alerta a Slack si un entrenamiento ML supera las 2 horas.

4. Integration (Conectores)

Catálogo amplio de conectores para bases de datos, cloud y APIs sin desarrollo artesanal.

Ej.: extraer de Google Analytics y cargar métricas en Salesforce.

Requisitos de un orquestador (2 / 2)

Los 7 pilares de la orquestación: Pilares 5 al 7

5. Scalability

Crecer horizontalmente en workers y asignar recursos elásticos en picos de demanda.

Ej.: motor de recomendaciones escalando en Black Friday.

6. Version Control

Pipelines como código en Git para auditoría, reproducibilidad y rollback inmediato.

Ej.: revertir una proyección financiera errónea en segundos.

7. Error Handling

Reintentos con backoff exponencial, cuarentena y rutas alternativas (fallbacks).

Ej.: API externa falla → 3 reintentos → conmuta a API de respaldo.

Apache Airflow 3: Arquitectura y Diseño de DAGs

De Airflow 2.10 al aislamiento con Task Execution API, Task SDK, XComs, idempotencia, control de flujo y Demo 1.

Convivencia en el mercado laboral

De Airflow 2.10 a Airflow 3.0+: ¿qué cambia?

Limitaciones históricas de Airflow 2.10

  • Workers con acceso directo a la BD: riesgo de seguridad y acoplamiento de librerías.
  • Sin versionado nativo de DAGs: un despliegue a mitad de run rompía la trazabilidad.
  • Solo Python en los workers y backfills bloqueantes por CLI.

Guía rápida de migración 2.10 → 3.0+

  • airflow.decorators → airflow.sdk
  • schedule_interval → schedule
  • days_ago(1) → datetime(2026, 1, 1)
  • Dataset → Asset · webserver → api-server
  • Auditoría automática: ruff check --select AIR30
Nuevo estándar cliente-servidor (AIP-72)

Arquitectura interna de Apache Airflow 3.0+

Modelo mental de ejecución

DAG, Task, DagRun y estados de una TaskInstance

DAG & Tasks: grafo acíclico en Python formado por operadores de Acción, Transferencia o Sensores.

DagRun & TaskInstance: cada ejecución concreta para un logical_date o evento de Asset.

Autoría de DAGs (1 / 2)

Sintaxis Clásica frente a TaskFlow API

Sintaxis Clásica (PythonOperator)
from airflow import DAG
from airflow.operators.python import PythonOperator

def procesar(): return 5 ** 2
def cerrar(): print("Fin")

with DAG("mi_dag", schedule="@hourly", ...) as dag:
    t1 = PythonOperator(
        task_id="procesar", python_callable=procesar
    )
    t2 = PythonOperator(
        task_id="cerrar", python_callable=cerrar
    )
    t1 >> t2  # Dependencia manual explícita
TaskFlow API (@dag y @task)
from datetime import datetime
from airflow.sdk import dag, task

@dag(dag_id="mi_dag_tf", start_date=datetime(2026, 1, 1),
     schedule="@hourly", catchup=False)
def flujo():
    @task
    def procesar() -> int:
        return 5 ** 2

    @task
    def cerrar(resultado: int) -> None:
        print(f"Recibido por XCom: {resultado}")

    cerrar(procesar())  # Dependencia + XCom automáticos

flujo()

Fiabilidad y semántica temporal

Idempotencia, logical_date y Backfills

Tres niveles de SQL

-- MAL: reejecutar duplica filas
INSERT INTO ventas VALUES ('2026-11-20', 1234.5);

-- BIEN: UPSERT idempotente
INSERT INTO ventas VALUES ('{{ ds }}', 1234.5)
ON CONFLICT (fecha) DO UPDATE SET total = EXCLUDED.total;

-- MEJOR: sobrescribir partición de forma atómica
DELETE FROM ventas WHERE fecha = '{{ ds }}';
INSERT INTO ventas SELECT ... WHERE fecha = '{{ ds }}';

logical_date vs. wall-clock time

  • Filtra siempre por {{ ds }}, jamás por datetime.now().
  • catchup=False en dev; usa Backfills nativos de Airflow 3 solo con tareas idempotentes.

Arquitectura de conectividad

Providers, Connections, Secrets Backends y Hooks

Pila en 4 capas (85+ Providers)

  • Connections: credenciales y endpoints fuera del código (conn_id, extra JSON).
  • Hooks (BaseHook): interfaz Python que gestiona sesiones y autenticación.
  • Operators / Transfers: tareas declarativas con Jinja.
  • Sensors & Triggers: espera asíncrona de eventos.

Resolución de secretos (first-hit-wins)

  1. Secrets Backend externo (AWS Secrets Manager, HashiCorp Vault, GCP, Azure) Solo lectura
  2. Variables de entorno (AIRFLOW_CONN_* en URI o JSON).
  3. Metadata DB cifrada con FERNET_KEY.

En cloud prioriza IAM Roles / IRSA / Workload Identity sin contraseñas estáticas.

def extraer_proveedores(ds: str = "") -> str:

Crear tu propio Conector (Custom Provider)

Hook + Trigger asíncrono + Operator deferrable
class MiCrmHook(BaseHook):
    conn_type = "micrm"
    def get_conn(self):
        c = self.get_connection(self.crm_conn_id)
        return crear_sesion(c.host, c.password)

class MiCrmTrigger(BaseTrigger):
    async def run(self):
        while not await job_listo_async(self.job_id):
            await asyncio.sleep(15)   # Nunca time.sleep()!
        yield TriggerEvent({"uri": self.uri})

class MiCrmExportOperator(BaseOperator):
    def execute(self, ctx):
        jid = MiCrmHook(self.conn_id).lanzar_export()
        self.defer(trigger=MiCrmTrigger(jid), method_name="done")
    def done(self, ctx, event): return event["uri"]

Evaluación rigurosa de LLMs y RAG

mlflow.genai.evaluate(): @scorer y LLM-as-a-Judge

Scorers deterministas + Juez trace-aware
@scorer
def cita_politica(*, outputs: str, expectations: dict) -> Feedback:
    ok = expectations["expected_policy"] in (outputs or "")
    return Feedback(name="cita_politica", value=ok)

juez_erp = make_judge(
    name="uso_herramienta_erp",
    instructions="Revisa {{ trace }} y confirma llamada ERP antes de reembolsar.",
    model="openai:/gpt-4o-mini",
)

res = mlflow.genai.evaluate(
    data=golden_dataset,
    predict_fn=asistente_carrefour,
    scorers=[cita_politica, Correctness(), Safety(), juez_erp],
)

Triada de Evaluación RAG

  • Context Relevance: calidad del recuperador (Recall@k, MRR, NDCG).
  • Faithfulness / Groundedness: 0 alucinaciones fuera del contexto.
  • Answer Relevance: responde realmente al cliente.

Combina siempre scorers deterministas (coste 0) + jueces LLM calibrados frente a humanos.

Evaluación reactiva con Airflow 3 Assets

  • DAG 1 (Ingesta RAG): actualiza documentos → embeddings en pgvector → emite Asset("s3://kb/corpus").
  • DAG 2 (Eval GenAI): disparado por el Asset o por un nuevo prompt @staging.
  • Lanza mlflow.genai.evaluate() y promociona @production o alerta con enlace a las trazas fallidas.

10 Reglas de Oro para llevarse a producción

Apache Airflow 3 y Conectores

  1. Airflow orquesta, no procesa: solo URIs en XCom.
  2. Idempotencia siempre: particiona por {{ ds }}.
  3. Cero secretos en código: Secrets Backends e IAM Roles.
  4. Espera eficiente: deferrable=True con Triggerer.
  5. Piensa en Airflow 3: airflow.sdk, Versioning y Asset.

MLflow 3, MLOps y LLMOps

  1. El código ML es el 5%: invierte en datos, Feature Store y Drift.
  2. Tracking limpio: log_metrics, firmas y evaluación holdout.
  3. Usa Aliases (@champion): los Stages están deprecados.
  4. Prompting científico: Prompt Registry + Tracing + genai.evaluate.
  5. Gobernanza GenAI: ResponsesAgent, AI Gateway y Data Flywheel.
